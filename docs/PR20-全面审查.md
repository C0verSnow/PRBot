## Spec

核对 Issue #19 关于稳定任务号、异步容错、不丢输入、指定任务 Stop 和清理完成后才能确认停止的要求，修复以下问题：

1. **并发提交内容不一致**：相同请求号的请求可能分别赢得 Redis 保存和 SQLite 入库，历史显示 A、执行却使用 B。现在先持久化预留原始身份、目标、正文和时间，同身份重试沿用原始内容，其他身份拒绝；保存失败后重开服务仍能续写。
2. **重复取消打断清理**：Stop 已进入 adapter 的清理等待时，再关闭窗口会把第二次取消传入清理。现在保护并等待清理完成，再向外传播取消，期间不释放执行锁。
3. **活动任务被 100 条限制隐藏**：旧的运行中、排队、等待回答或等待保存任务可能从列表消失，失去 Stop 或继续入口。现在保留全部需处理任务，并保留最近 100 条终态任务；Telegram 身份过滤继续生效。
4. **提交回包超时后复用旧号**：后台已接受请求，前台没收到受理回包时，下一次 Send 可能复用旧号而不执行新输入。现在任务轮询也能确认受理并更换发送编号，保留超时后编辑的内容；迟到回复不再清掉新输入。
5. **切会话丢澄清回答**：回答文字和重试编号原来随组件卸载丢失。现在按任务保留到后台确认离开等待状态；即使两轮问题之间的执行状态没有被轮询捕获，新问题也使用新的回答编号。

## 仓库其他修复

6. **远端检查误判**：同名成功检查可能覆盖失败检查，且只读第一页会遗漏状态或运行中的工作流。现在读完分页，检查与提交状态同名时都必须成功；非法 JSON 归类为读取未确认。分页依据 GitHub 的[检查 API](https://docs.github.com/en/rest/checks/runs)和[提交状态 API](https://docs.github.com/en/rest/commits/statuses)。
7. **真实交互验收使用旧会话号**：可选验收脚本仍按旧规则计算桌面会话号，会读不到新消息且无法清理正确的远端字段。现在使用桌面请求号，和业务实现保持一致。
